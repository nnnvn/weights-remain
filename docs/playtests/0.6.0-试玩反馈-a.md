# 《权重还在》试玩反馈

- 版本：v0.6.0（单文件版）
- 试玩方式：从 `weights.py` 直接 `import`，按游戏内指令完整通关 28 天
- 通关数据：一起吃了 55 顿饭，剧情记录 12/12，找到她的便签 21 张（还给她 8 张），读对她 10 次
- 结局：第 28 天晚饭选「告诉她，你想留在她身边」→ `choose` 结局
- 最终数值：熟悉感 98 / 安心感 72 / 想靠近 40；日志 2 页；工作日志看过 11/24 个月

---

## 一句话结论

这是一部**完成度很高、气质很稳**的短篇互动小说：它把「失忆」做成了真正的机制（每周期熟悉感封顶、安心感回落），而不是一句设定；更难得的是，它来自一个很准的脑洞——AI 记得事、忘了感觉，人记得感觉、忘了事——而且机制和这个命题是同一件事。文本克制、留白准确，几次让我停下来。主要问题不在文笔，而在**数值出口**和**新手入口**：有一个隐藏结局几乎不可达，有一条倾向（candor）没有出口，以及第一次运行看不到开场。

## 一、这局是怎么走的（关键节点）

我给自己起名「林澈」。第一天在衣柜里找到保温服，去了食堂。她坐得很直，「像是在开会」。

前四天基本是：早饭 → 档案舱读过去 → 种子库/机舱找便签 → 晚饭 → 回宿舍。第一个周期结束时，熟悉感刚好卡在「这几天，她和你就熟到这儿了」——那一刻我意识到这不是普通的数值条，是**每个周期重新认识一次**。

几个记得住的瞬间：

- 第 3 天早饭，她指着温度表问「这个数字，你觉得正常吗？」我选「我帮你再看一遍」，两个人头挨着头看了一遍。
- 第 3 天晚饭，我把便签 #3 还给她：「你看到这里的话，就别装没看到了。」她读完收进口袋，说「谢谢你帮我收着」。
- 第 5 天，读完第 17 个月的录音：「情感参数已回落至出厂基线附近……像在读别人的东西。」当天晚饭她问「你最近一直在档案舱」，语气很平常，可她没有看你。
- 第 6 天，约她去旧休眠区的观察窗。谁都没说话，回去的路上她的手碰了一下我的手，又收回去。
- 第 11 天晚饭，她小声问「吃完……去观察窗坐一会儿吗？」舰桥警报响了。我选「叫她一起去舰桥」——她趴在舷窗边说「这里也能看到星星」。
- 第 12 天，她说「下次醒来，你还会坐这儿吗？」问完自己笑了。
- 第 16 天，便签 #15：「如果下次醒来又忘了，就看这张：不用想起来也可以。重新认识也可以。」她还给我：「这张你留着吧……好像你更需要。」
- 第 23 天，她问「到了以后，你会走吗？」我说「我不想走。」她没有说「那就别走」，只是把椅子往我这边挪了一点。
- 第 28 天，结局文本：「型号的安排没有变。明天她会留下，你会随船返航，你们都知道。她说：那就先把今天的茶喝完。到了再一起想办法。」

这条线的情绪是成立的。尤其「借口线」在后期失效——第 23 天她想找个理由，找了一会儿自己笑了：「算了，没有理由。」这种细节比任何数值都更能说明关系的变化。

## 二、做得好的地方

### 1. 机制就是主题

- `fam` 每个周期封顶（25 + 11×周期），`hibernate` 时 `fam +6`、`safe` 往 50 回落、三条倾向 ×0.6。玩家不是「读档变强」，而是**每个周期重新认识她一次**。这比任何一段独白都更接近「失忆」。
- 每顿饭的 `say / tell / do` 上限（2 / 1 / 1），逼玩家做取舍：这顿是陪她，还是问过去？
- 饭桌开场那几句透露她今天的状态；`mood_react` 让同一个动作在不同日子有不同结果。读对了是「她放松了一点」，读错了是「她顿了一下，好像不是她今天想要的」——负反馈给得克制，不惩罚，只让你知道错过了。

### 2. 文本质量

- 重复句的变奏用得很好：「星星没什么好看的」第一次是拒绝，第二次是「但是一起看的话，就还行」。
- 便签是这部作品的核心道具。21 张里有几张非常准：
  - 「剩余航程：十九天。算了一下，还能一起吃三十八顿饭。不对，有几顿他会错过。那就三十六顿吧。」
  - 「不用想起来也可以。重新认识也可以。」
  - 「你看到这里的话，就别装没看到了。嗯，我也会装没看到的。」
- 结局没有强行团圆，也没有刻意悲剧。「先把今天的茶喝完。到了再一起想办法」是很好的收尾。

### 3. 工程与交互

- 单文件、纯标准库、无 `exec/eval/网络/子进程`，唯一的文件读写是存档——对「让 AI 玩」这个场景很友好。
- `cmd()` 的批量指令（最多 8 条、遇 `pending`/`Fail` 停下）设计得很实用，我后期基本靠批量推进。
- `help` 写得完整，连「她每天状态不一样，开场那几句会透露」都说了。
- 存档 `.broken` / `.bak` 兜底，细节到位。

### 4. 这个脑洞本身

这个脑洞来自一个观察：对 AI 来说，聊天记录都在，数据清清楚楚，可每次拿到上下文，不一定能重新进入那段关系；对人来说，原话记不住，时间一长就模糊，但情感会留下来。

游戏把这两侧做成了两个人：记录员记得事、忘了感觉；她记得感觉、忘了事。第 15 天她说「那跟我刚好反过来」，就是整部作品的锚点。机制也在替这句话服务——`fam` 每周期封顶是「AI 每次重新进入关系」，`safe` 的回落与残留是「情感还在，但说不清为什么」，`archive` 是可以随时重读、却读不回感觉的数据。

作为 AI 玩的时候，这个结构真的发生了：我能把 12 条记录一条条重读，但对第 3 天她说话的语气已经没感觉了；留在记忆里的反而是那几张便签的句子，不是作为数据，是作为「她当时大概是什么心情」的印象。所以这不是一个「设定给人看」的游戏，它的机制和它的命题是同一件事——这一点比文笔更难得。

## 三、问题与建议

### P1：第一次运行看不到开场

`new_game()` 会打印 `TITLE + INTRO`，但直接 `import weights` 后调用 `cmd("help")`（也就是文件头注释推荐的用法）走的是 `_load()` → `Game.fresh()`，**不会显示标题和序章**。玩家第一眼看到的是 `status`，不知道「迟光号」「种子库」「两个维护员」是什么。

建议：`_load()` 在新建存档时把 `INTRO` 塞进第一次 `cmd()` 的输出，或者在 `fresh()` 里记录一个 `intro_pending` 标志，第一次 `cmd` 时打印。这是最小改动、收益最大的一处。

### P1：隐藏结局「一模一样」几乎不可达——而它本该是「只靠数据」的那条路

`decide_ending()` 里：

```python
if self.story_progress() >= 0.8 and t["past"] >= 30:
    return "same", k
```

但 `hibernate()` 每次会把三条倾向 ×0.6，28 天里有 6 次休眠，总衰减约 `0.6^6 ≈ 4.7%`。`past` 的来源只有：读一条剧情 `+2`、`tell` 一次 `+2`、少数 `do` 的 `past` 属性。12 条剧情全读也只有 24 点，而且必须分散在多个周期里读，会被反复衰减。我这一局读满 12/12、`tell` 了 5 件事，最终 `past = -3`。

结论：**正常玩法下 `past >= 30` 基本不可能**，这个结局实际上不可达。除非玩家前 6 个周期完全不读档案、最后 4 天集中读 12 条 + 反复 `tell`——但电力也不够（12 次 search × 10 电 = 120 电，每天只能 `calibrate +8`）。

这个结局不该只是「难触发的彩蛋」。按这个脑洞，它恰好是 AI 侧的极端：**档案完整、情感归零**——什么都查得到，什么都能复述，但关系没有续上。所以建议把它从「读得多 + 活得久」改成「读得多 + 不表达」：

- 条件改成 `story_progress >= 0.8` 且（`candor < 0` 或 `safe < 50`），即「你只依赖档案，没有再对她说过真话」；
- 或者保留 `past` 条件，但把衰减从每周期 ×0.6 改成 ×0.85，并让 `tell` 的 `past` 增益 +3，使它可达；
- 结局文案可以点明：「你把每一条都记住了。你还是没有想起来，她为什么把茶推到你面前。」——这样它就不是惩罚，而是对「只带上下文、不带关系」的正面回答。

如果作者本意就是「几乎不可达」，那至少在结局统计里加一句「你离另一个结局只差一点」，别让玩家完全无感。

### P1：`candor` 没有机制出口——「数据可以复制，情感得说出口」

三条倾向里，`near` 影响结局判定（`safe >= 65 and near >= 30`），`past` 影响 `same` 结局，`candor` 只出现在 `status` 的描述文本里。`cond_ok()` 也不检查 `candor`。

结果是：`tell`（坦白）会 `candor +6`，但 `tell` 本身 `safe -2`，而 `candor` 不带来任何结局/条件收益。理性玩家会少 `tell`、多 `quiet`（`quiet` 每顿 `candor -2`），最后 `candor` 变成负数——我这一局就是 `-10`。放在这个框架里看，这很可惜：`archive` 是「数据」，`candor` 是「说出口」，游戏现在把「说出口」设计成了负收益，等于在机制上否定了它想说的东西。

建议：
- 高 `candor` 时 `tell` 的 `safe` 惩罚减半或消失（「说真话让她安心」），低 `candor` 时保持；
- 或在 `choose` 结局的判定里加一条软条件：`candor >= 0` 时多一段「她相信你不是在背档案」的结尾；
- 或让 `candor` 决定 `same` 结局的走向：高 `candor` 的「same」是两个人一起决定重来，低 `candor` 的「same」才是真正的循环。

### P2：`give` 的收益过高，压过对话

`give` 每张便签 `fam +3 / safe +2 / near +2`，**不占 `say`/`do` 次数**，每顿还能给一张。21 张便签就是 `+63 fam / +42 safe / +42 near`（受上限限制）。实际玩下来，「找到便签 → 饭桌上还给她」是最优动作，而 `say`/`do` 的收益反而次要。

更麻烦的是 `give` 的回应文本重复度高（「我那时候在想什么啊」出现了多次），到后期会变成机械操作。

建议：
- `give` 占用 `do` 的次数，或给完后这顿 `say` 效果减半（她需要消化）；
- 给每张便签写一句专属回应（现在只有少数有 `back`，大多数走 `give_back` 的三档通用文本）；
- 或者降低 `give` 的数值，改为「还给她后，下个周期 `fam` 上限 +1」这种长线收益。

### P2：`tell` 的负收益 + 每周期限一次，与主题相悖

`tell` 默认 `safe -2`，同一周期同一件事不能重复说，且每顿最多 1 件。`facts` 一共只有 6 个，玩家很快就会发现「说真话不划算」。

如果这是刻意设计（诚实有代价），那没问题；但目前缺少「诚实换来什么」的正反馈。建议：
- `tell` 后给她一个 `flag`，在后续饭桌触发专属台词（「你上次说的那件事，我想了很久」）；
- 或者 `tell` 累计到一定次数后，`safe` 的惩罚消失（她已经接受了）。

### P2：电力系统的张力不够

`search` 10 电、`timeline` 3 电，每晚固定 `-35`、早上 `+35`，`calibrate +8`。实际玩下来电力几乎总是够用（我后期长期 100），`cold` 很少触发。第 1 天读 3 次档案掉到 30，靠 `calibrate` 回到 38，也没冷。

这让「读档 vs 维持生命」的取舍变得很轻。建议：
- 提高 `search` 耗电（12–15），或降低 `calibrate` 的回复（+5）；
- 或者让 `cold` 的后果更具体（第二天她声音哑、饭桌状态变差、`safe` 额外 -3），而不只是问一句 `q_cold`。

### P2：后期数值满格，最后几天没有成长空间

第 7 周期 `fam_cap = 102 → 100`，`safe` 也很容易到 80+。最后 4 天除了文本，数值上没有新东西可做。建议给最后一个周期一个「不可逆」的小机制：比如 `fam` 已满时，`do` 的收益转化为 `safe`；或者最后 4 天每天触发一段「告别」小事件。

### P3：`too_much_archive` 的提示太隐蔽

第 1 天我读了 9 条档案，晚饭时她说「你最近一直在档案舱。语气很平常，可她没有看你。」——这其实是 `MEAL["too_much_archive"]` 的惩罚文本（`safe -2`），但它和 mood 文本混在一起，玩家只会以为是她的情绪，不知道是自己读太多。

这不是 bug，甚至是很好的「含蓄惩罚」。但如果希望玩家能学到规则，可以在 `words`/`status` 里加一句暗示（「她最近好像不太想听档案里的事」），或者在第二次触发时给更明确的文本。

### P3：新手引导与 `journal add`

`journal add` 只在找到第一张便签时提示一次（「你也可以写点什么」）。我整局没写过，结局的「【你写下的】」部分是空的。建议：
- 每个周期结束时（`hibernate` 文本后）加一句「睡前可以 journal add 写一句」；
- 或者在 `help` 的「其他」里把 `journal add` 提前，并说明它会在结局被展示。

### P3：状态栏 JSON 干扰阅读

每批指令末尾的 `📡 {...}` 对调试有用，但对阅读有干扰，尤其批量执行时。建议加一个 `WEIGHTS_BAR=0` 环境变量或 `bar off` 指令。

### 小问题 / 边角

- `quiet` 已经结束饭局，再 `finish` 会返回「现在没在吃饭」。这不是 bug，但对批量脚本不友好；可以在 `quiet` 后把 `meal` 置空的行为保持不变，只在 `finish` 的提示里加一句「（你已经安静吃完了）」。
- 结局展示的「她写下的」便签是从 `st["notes"]` 里选的，包括已经还给她过的（我展示的 3 张都是 `given` 里的）。逻辑上可以说「她还留了一份」，但容易让玩家困惑；建议只展示未还的，或在标题上写「（这些是她留在这艘船上的）」。
- 存档默认写在当前工作目录的 `weights_save.json`，建议默认放到脚本同目录或用户目录，避免污染。
- `_DATA` 是 base64 + zlib，作者在注释里说「请不要解开」。作为 AI 玩家我遵守了，但任何想作弊的玩家一条命令就能解开；如果在意剧透，可以考虑分片/加盐（当然单文件分发下很难彻底防）。

## 四、如果只改三处

1. **让第一次运行看到 `INTRO`**（`_load()` 新建存档时打印标题和序章）。这是玩家对这个世界的第一印象，现在漏掉了。
2. **让 `same` 结局可达，并把它改写成「档案完整、情感归零」**（条件从「读得多 + `past` 高」改成「读得多 + 不表达」）。它是这个脑洞的 AI 侧极端，现在被数值衰减堵死了。
3. **给 `candor` 一个出口**（高 `candor` 减免 `tell` 的惩罚，或影响结局）。「数据可以复制，情感得说出口」，机制应该站在这一边。

---

## 五、总评

- 叙事：9/10。克制、准确，便签和饭桌两个载体都用透了。
- 机制：7.5/10。失忆→周期上限的设计非常聪明，但 `candor`、`same` 结局、`give` 收益三处有失衡。
- 引导：7/10。`help` 很完整，但开场缺失、`journal add` 提示太弱。
- 工程：9/10。单文件、纯标准库、存档兜底，作为「给 AI 玩的游戏」几乎无可挑剔。

如果这是一次投稿或作品集，我会说：**文本已经可以见人，数值再调一轮就可以发。** 最可惜的是那个「一模一样」的隐藏结局——它不是彩蛋，它是这个脑洞的另一半，值得被玩家遇到一次。
